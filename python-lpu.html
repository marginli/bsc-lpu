開場先講四個詞

這一頁會反覆出現四個字眼。先各給一句話，之後不再解釋。

函式function

一段有名字的程式，吃進幾樣東西、吐出一個結果。hotspots(遮罩, 密度場, 75) 就是一個函式：給它三樣東西，它還你一批熱點體素。名字後面的括號就是「吃進什麼」。

類別class

把一批資料和處理那批資料的動作綁在一起的盒子。整條管線只有兩個：Config 裝所有參數，Brain 裝所有資料。

模組module

一個 .py 檔案。import lpu_lib 的意思是「把 lpu_lib.py 這個檔案裡的東西拿過來用」。

參數parameter

程式裡寫死的數字——門檻、比例、跑幾次。這一頁最重要的一個概念：換掉一個參數，結論就可能改變，但程式不會告訴你。

骨架五個問題

拿到一份 AI 寫出來的程式，不論它算的是果蠅腦、問卷資料還是影像，都可以問同樣五個問題。每一個問題只需要看程式的一小塊。

#問題要看哪裡為什麼是這一個
1哪些數字決定了結論？Config結論通常靠十幾個數字撐著，不是靠一千行
2資料是怎麼進來的？Brain讀錯資料的話，後面每一步都會很順利地算出錯的答案
3這一段在做哪一步？函式名 ↔ 步驟的對照表有對照表才能只讀你關心的那一段
4它怎麼證明自己沒寫錯？expected.json沒有這一塊，「跑完了」只代表沒當掉

三個檔案的分工

run_lpu.sh
門

在終端機打的那一行。它只做四件事：檢查環境、跑、核對、列出產出。55 行，沒有任何計算。

run_lpu.py
順序

十四條指令收成十二個函式（指令 10＋11、12＋13 各併成一個）。它只管先做什麼、再做什麼、把什麼印出來，不管怎麼算。1,050 行。

lpu_lib.py
做法

參數、資料、七個步驟的演算法、畫圖。要改結論就改這裡。553 行。

這個切法有一個實際的用處：你想改什麼，就知道要打開哪一個檔案。想換一個參數重跑 → lpu_lib.py 最上面；想知道第 7 步在第 6 步之前還是之後 → run_lpu.py 最下面的順序表；想在別台機器跑 → 只碰 run_lpu.sh。

2問題一：哪些數字決定了結論

拿到一份程式，第一件事是找出所有寫死的數字。

不是看它怎麼算，是看它用了哪些門檻。散在一千行各處的話，你永遠不會知道結論靠什麼撐著。

整條管線的所有參數都在 lpu_lib.py 最上面的 Config 裡，而且刻意分成三組：

@dataclass
class Config:

    d06: Path = Path("/home/wanjuli/claude_linux/BSC_plan/D06")

    min_cluster_frac: float = 0.01  # 步驟 4：群要大於腦區體積的 1%
    overlap: float = 0.50           # 步驟 5：重疊超過 50% 才招募

白話：這是一張設定表。每一行是「名字 ＝ 數字 ＋ 一句說明」。程式跑的時候，任何地方要用到「上四分位」，都是回來讀這張表的 quartile，不會自己寫一個 75。所以要改一個門檻，只要改這裡一個地方。
藍底標起來的那兩段，就是 PART 4 結論五那張表——十三行程式碼、十項決定。論文沒有給這些數字，是我們自己決定的。它們跟上面那組（論文給的）長得一模一樣、寫在同一個地方、用起來也沒有差別——而這正是最容易出事的地方。把它們分成兩組並註明來源，是為了讓讀的人一眼看出「哪幾個數字是有出處的，哪幾個是我們選的」。

它每一次跑都會把這組數字印出來

Config 裡有一個叫 describe() 的函式，作用只有一個：把「自己決定的」那一組印在螢幕上。每次執行都印，不管你要不要看。

為什麼要強迫自己看？因為半年後回來看 out/ 裡的結果，你不會記得當時 f_ln 設的是 0.8 還是 0.9。把它印在紀錄的最前面，等於每一份結果都自帶產生它的條件。

3問題二：資料是怎麼進來的

讀錯資料的程式不會當掉，它會很順利地算出錯的答案。

所以第二個要看的地方，是「檔案變成數字」的那一段——尤其是座標怎麼對上。

這條管線要同時用兩套座標：

D03 的標籤格D06 的骨架體素
是什麼每一格記著「這裡屬於哪個腦區」每一筆記著「某顆神經元經過這一格」
格子大小1 µm邊長 2 個標籤格
怎麼存一個 311 × 611 × 956 的三維陣列一個整數 vox，三個軸的位置編在一起

「編在一起」的意思是：一個整數同時記著三個軸的位置，要用的時候得拆開。Brain 在載入的當下就拆一次，之後全程共用：

G = cfg.d06_grid                          # 512
self.ix = (self.vox % G).astype(np.int64)         # ← 左右
self.iy = ((self.vox // G) % G).astype(np.int64)  # ← 背腹
self.iz = (self.vox // (G * G)).astype(np.int64)  # ← 前後
白話：這是「除法與餘數」而已。想像門牌號碼寫成 樓層 × 10000 ＋ 排 × 100 ＋ 號，要拆回來就是除一除、取餘數。% 是取餘數、// 是取商。整條管線只有這四行在做這件事，PART 4 有九份各自寫過一次。
右邊那三個註解是這一頁排版時加的（原始碼裡寫成上一行的一句話）。而重點正在這裡：ix 是左右、iy 是背腹、iz 是前後這件事，不是從檔案的標頭讀來的——標頭沒寫。它是 PART 4 的指令 1 用三組解剖關係反推出來的：兩側視葉的重心相差 668 格，而且幾乎只差在同一個軸上，那個軸就是左右。

這種「靠外部知識才能確定的事」，是讀 AI 寫的程式時最該停下來查的一類。程式把軸接反了也照樣跑得完，只是所有結果都左右顛倒，而且不會報錯。

後面所有步驟共用的那張表

Brain 算完座標之後，會做一張表 contact，它是後面好幾步的共同輸入：

@property
def contact(self) -> np.ndarray:
    """神經元 × 腦區的體素數矩陣 C。第 0 欄（腦區外）已歸零。"""
    if self._C is None:                     # 只算一次，算完存起來
        N, R = len(self.neurons), len(self.names)
        L = self.region_of_voxel
        C = np.bincount(self.nid.astype(np.int64) * R + L,
                        minlength=N * R).reshape(N, R)
        C[:, 0] = 0
        self._C = C
    return self._C
白話：C 是一張 28,573 列 × 76 欄的表。第 i 列第 j 欄的數字是「第 i 顆神經元有幾個體素落在第 j 個腦區裡」。LN 判準、神經束驗證、合併判斷，三步都只是在對這張表做算術。
if self._C is None 那一行是「算一次就好」的寫法。第一次有人要這張表時才算，算完存在 self._C 裡；第二次以後直接拿現成的。這張表要掃過 1,189 萬筆「某顆神經元經過某個體素」的紀錄，重算十次就是白白多花十倍時間。讀程式時看到這個形狀，就知道它下面那段是「貴」的。

細讀之一：最短的那個函式

def hotspots(mask, v, q):
    """取上四分位以上的體素。

    佔比必然接近 25%，因為「上四分位」的定義就是排到 75% 的那個位置。
    這個 25% 不是資料的性質，是分位數定義的必然結果。
    """
    return mask & (v >= np.percentile(v[mask], q))
白話，一行拆成三件事：先 v[mask] 把腦區內的密度值挑出來；再 np.percentile(..., 75) 找出排到 75% 那個位置的值；最後 mask & (v >= 那個值) 選出「在腦區內、而且密度不低於那個值」的格子。一行程式就是 PART 2 的第三步。
真正要讀的是那段說明文字。它講的不是「程式怎麼寫」，而是「不要把結果讀錯」——熱點永遠佔 25%，這不是果蠅腦的性質，是四分位這個定義造成的。看到跑出來的數字是 25.0% 就以為發現了什麼，是最容易犯的錯。

讀 AI 寫的註解時，值得先分類：這一句是在解釋程式（可以跳過），還是在解釋結果（一定要讀）。

細讀之二：為什麼一個迴圈要跑九次

def cut_sweep(P, thr, cfg, rng, detail=False):
    """掃切割高度，並把體素順序打亂重跑 n_shuffle 次。"""
    cuts = cfg.cuts
    runs, root = [], None
    for t in range(cfg.n_shuffle):                    # 跑九次
        Q = P if t == 0 else P[rng.permutation(len(P))]   # 第一次不打亂，之後都打亂
        D = pdist(Q)                                  # 兩兩距離
        Z = linkage(D, "average")                     # average linkage 就是 UPGMA
        runs.append([...每一個切割高度剪出幾群...])
        del D                                         # 用完立刻丟掉，這東西很大
    ...
白話：同一份資料，換九種排列順序，各分群一次，看答案一不一樣。如果九次的答案都相同，那個答案就可信；如果九次不一樣，那就不是「答案」，是「其中一種答案」。
為什麼順序會影響答案？AL_R 有 3,130 個熱點體素、4,896,885 對距離，但相異的距離值只有 557 種——體素排在整齊的格子上，距離大量重複。UPGMA 每一步要挑「最近的一對」，遇到平手時，選哪一對取決於它們在陣列裡的先後。順序一換，樹就不一樣。

實測：切割高度取 6 時，打亂九次得到 13、13、13、14、14、14、15、15、15 群。

if t == 0 這種分支，讀到就要停一下。它的意思永遠是「第一次跟其他次不一樣」。這裡是「第一次用原本的順序，其餘八次打亂」——所以九次裡有一次是原始答案，八次是對照。如果沒注意到這一行，會以為它跑了九次隨機、實際上是一次原始加八次隨機。

5問題四：它怎麼證明自己沒寫錯

「跑完了、沒報錯」只證明程式沒當掉，不證明它算對了。

要看的是：有沒有一份寫在程式外面的預期答案，跑完會自動核對。

白話：每一行是一項「應該是多少」。path 是「去產出的哪一份檔案、找哪一個欄位」，want 是應該得到的值，tol 是允許的誤差（小數才需要）。跑完之後 verify 會把 47 項逐一比對： 
$ python3 run_lpu.py verify
核對 47 項：通過 47、不符 0、還沒跑 0
全部通過。
最有用的驗收項，是那幾條「預期它失敗」的。上面那條 partial_cells 的 want: 0 記的是「指令 9 應該找不到任何可用的參數組合」。如果哪天這一項變成不是 0，代表資料換了、或是招募那一步被改動過——而那正是最需要被通知的時候。

驗收表不只用來確認成功，也用來釘住已知的失敗。

為什麼要放在程式外面的一個檔案？因為它是「答案」，不是「作法」。放在外面，改答案不必動程式，改程式也不會順手把答案一起改掉。把預期值寫進程式裡自己跟自己比，等於沒有比。

6問題五：跑不出東西的時候會怎樣

最危險的不是報錯，是不報錯。

一支程式在資料撐不住的時候，可以選擇三件事之一。選哪一件，是寫程式的人的價值判斷，不是技術問題。

做法使用者看到什麼後果
照樣算下去一份完整、漂亮的結果最糟。看不出有問題，數字會被引用
印一行警告再算下去幾百行輸出裡的一行小字幾乎等於沒印。往下捲就看不到了
停下來沒有結果，只有一段說明為什麼停使用者必須自己決定要不要繼續

PART 4 的指令 9（滾雪球招募）在這份資料上跑不出中間結果：掃「撐大 2 到 5 格 × 重疊門檻 0.3 到 0.7」共 20 種組合，每一種的答案不是 1 顆（只有種子）就是 723 顆（整池）。這一版採取第三種做法：

「收一部分」＝結果落在 2 到 722 之間的格子數：0 ／ 20

┌──────────────────────────────────────────────────────────────────────
│ 這一步沒有可用的操作區間。
│ 20 種參數組合，每一種的結果不是 1（只有種子）就是 723（整池）。
│ 沒有任何一種設定收到「一部分」。
│
│ 這不是參數沒調好。論文要求從「最小的」LN 出發，但一顆小的神經元
│ 撐大之後仍然裝不下一顆大的一半體積，所以要嘛收不到，要嘛一旦撐得
│ 夠大就整池全收。
│
│ 主程式在這裡停下來，不往下產出看起來完整、其實沒有意義的結果。
│ 要繼續，請加上 --force-recruit：接下來的一切都建立在
│ 「撐大 4 格」這一種讀法上，而那是唯一跑得動的讀法，不是驗證過的。
└──────────────────────────────────────────────────────────────────────
白話：程式在這裡把選擇權交還給人。它把量到的事實（20 種組合、沒有一種收到一部分）、它的判讀（不是參數沒調好）、以及繼續下去的代價（後面的一切都只是一種讀法）講完，然後停住。要往下跑，得自己打出 --force-recruit 這幾個字。
那個旗標的作用不是技術上的，是紀錄上的。它讓「我知道這一步沒有根據，但我還是要往下跑」變成一件必須打出來的事，而且會留在指令紀錄裡。沒有旗標的話，這個決定會消失得無影無蹤。

在自動化的腳本裡也一樣要看得見。run_lpu.sh 帶著這個旗標，而理由就寫在旗標旁邊，不是寫在另一份文件裡：

# --force-recruit 的意思：
#   指令 9（滾雪球招募）在這份資料上沒有可用的操作區間——20 種參數組合，
#   結果不是「只有種子 1 顆」就是「整池 723 顆」，沒有一種收到一部分。
#   主程式預設會在那裡停下來，不產出看起來完整、其實沒有意義的結果。
#   這裡加上旗標讓它往下走，是為了把後面幾步也跑出來；但要記得，
#   之後每一個數字都建立在「撐大 4 格」這一種讀法上。
"$PY" run_lpu.py all --force-recruit
這是拿到 AI 寫的程式時最該檢查的一件事。問它：資料不夠、條件不成立的時候，你這支程式會怎麼做？如果答案是「照樣算完」，那它產出的每一份結果都需要你自己去判斷可不可信——而你多半沒有那個資訊。

三件會咬人的事

要注意的為什麼
畫圖前要先設 Agg沒有螢幕的機器（伺服器、容器、ssh 連進去的工作站）直接畫圖會找不到顯示裝置而中斷。整條管線只有 setup_matplotlib() 一個地方在做這件事，所以只有一個地方需要對
圖裡不要放中文新機器不一定裝了中文字型。字型不在的時候 matplotlib 不會停，它照樣把圖存起來，只是每個中文字都變成空白方塊。七張圖的文字全部是英文，說明一律寫在網頁上

整條管線的瓶頸不是算力，是資料。全腦 75 區跑完只要 94 秒，而其中 54 區的 LN 候選少於十顆，根本沒有東西可以分群。換一台更快的機器，不會讓那 54 區變得可以分析。看到一份程式跑得很慢時值得先問：慢的是計算，還是根本在等一份不存在的資料？

收尾一張可以帶走的檢查清單

這五個問題跟果蠅腦沒有關係。任何一份 AI 寫給你的分析程式，都可以照這個順序問一遍。

#問題怎麼問答不出來代表什麼
1參數在哪裡「把所有寫死的門檻、比例、次數列給我，並標出哪些有出處、哪些是你自己決定的」你不知道結論靠什麼撐著
2資料怎麼進來「單位是什麼、座標軸誰是誰、這個判斷是從檔案讀來的還是你推的」可能整份結果左右顛倒，而且不會報錯
3哪一段做哪一步「給我一張表：我的第幾步 ＝ 你的哪個函式」你只能整份接受或整份不信，無法逐段檢查
4怎麼證明沒寫錯「把預期值寫成一個獨立的檔案，跑完自動核對」「跑完了」只等於「沒當掉」
5撐不住時會怎樣「資料不夠、條件不成立的時候，你會停下來還是照樣算完」最危險的一項。你會拿到一份看不出有問題的結果
五個問題裡只有第四個在問「算得對不對」。其餘四個問的是參數的來源、資料的意義、能不能逐段對照、撐不住時怎麼處理——全部是「這份結果能不能拿去用」的問題。算法對不對，AI 通常比你會判斷；但這四件事只有你能判斷，因為只有你知道這份資料是怎麼來的、要拿去回答什麼問題。
回到這堂課的起點。PART 1 問「一個腦區的邊界該畫在哪裡」，PART 2 把它變成七個步驟，PART 3 把七個步驟變成十四條指令，PART 4 讓 AI 真的跑了一遍，這一頁把跑出來的東西整理成看得懂、帶得走的三個檔案。

五個部分裡，只有 PART 4 那一步是 AI 做的。其餘四步——決定要問什麼、把問題寫成步驟、把含糊的地方指定清楚、判斷跑出來的東西能不能用——都還在人這一邊。
